# XAUUSD MT5 EA Research Methodology

## 1. Purpose

This document defines the research, implementation, and validation methodology used for Expert Advisors in the `xauusd-mt5-ea-research` repository.

The objective is to convert trading hypotheses into explicit MQL5 rules and evaluate them using reproducible MetaTrader 5 backtests.

The methodology separates four components:

```text
Trading Hypothesis
        ↓
Rule Definition
        ↓
MQL5 Implementation
        ↓
MT5 Backtest
        ↓
Evidence
        ↓
PASS / FAIL
```

A strategy is not considered successful simply because it has been implemented successfully.

Implementation validity and trading performance are evaluated separately.

---

## 2. Research Principles

Each EA should follow these principles:

1. Define a trading hypothesis.
2. Convert the hypothesis into explicit rules.
3. Implement those rules in MQL5.
4. Preserve the source code used for testing.
5. Backtest the implementation using MetaTrader 5.
6. Preserve the original Strategy Tester evidence.
7. Record both positive and negative results.
8. Never remove a failed strategy merely because the result is poor.
9. Never claim profitability without supporting test evidence.
10. Keep baseline results available for comparison with future variants.

The repository is therefore a research record, not only a collection of profitable strategies.

## 3. Repository Structure

Each research experiment is separated into implementation, evidence, and research documentation.

```text
xauusd-mt5-ea-research/
│
├── EAs/
│   └── EA-XXX_Strategy_Name/
│       ├── EA-XXX_Strategy_Name.mq5
│       └── README.md
│
├── Backtest/
│   └── EA-XXX_Strategy_Name/
│       ├── README.md
│       ├── Strategy Tester report
│       └── Strategy Tester charts
│
├── Research/
│   └── README.md
│
├── docs/
│   └── methodology.md
│
└── GitHub_Profile/
    └── README.md
```

### `EAs/`

Contains the actual MQL5 implementation.

The EA README should document:

- strategy logic,
- entry conditions,
- exit conditions,
- risk management,
- execution filters,
- input parameters,
- and implementation behavior.

Performance claims should not be placed here unless supported by corresponding backtest evidence.

### `Backtest/`

Contains empirical evidence generated by MetaTrader 5 Strategy Tester.

The directory should preserve the original report and associated charts whenever available.

The Backtest README summarizes the test configuration, metrics, and result.

### `Research/`

Documents the hypothesis being investigated, observations from the experiment, research conclusion, and possible future research questions.

### `docs/`

Contains repository-level methodology and documentation.

Format:

```text

```

Example:

```text

```

The same identifier should be used consistently across implementation and backtest directories.

```text
EAs/

└── EA-058_Wedge_Break/
```

This makes the source implementation directly traceable to its corresponding test evidence.

## 5. Research Workflow

The standard workflow is:

```text
STEP 1
Define hypothesis
      ↓
STEP 2
Translate hypothesis into deterministic trading rules
      ↓
STEP 3
Implement EA in MQL5
      ↓
STEP 4
Compile and verify execution
      ↓
STEP 5
Run MT5 Strategy Tester
      ↓
STEP 6
Save original report and charts
      ↓
STEP 7
Extract key metrics
      ↓
STEP 8
Evaluate result
      ↓
STEP 9
Record PASS / FAIL
      ↓
STEP 10
Preserve baseline for future comparison
```

Each stage should remain traceable.

## 6. Hypothesis Definition

Before evaluating an EA, its trading hypothesis should be expressible in a simple statement.

For example, EA-058 tests the hypothesis that:

> A confirmed breakout from a contracting wedge may produce sufficient directional continuation to create a repeatable trading edge on XAUUSD.

The hypothesis should describe what market behavior the EA attempts to exploit.

It should not assume that the behavior is profitable before testing.

---

## 7. Rule Definition

Visual trading ideas must be converted into deterministic conditions before they can be objectively tested.

For example:

```text
Visual concept:
Contracting wedge

↓ Convert to measurable conditions

Recent Pivot High < Previous Pivot High

Recent Pivot Low > Previous Pivot Low

↓ Define breakout

Closed candle > projected upper boundary + buffer
→ BUY

Closed candle < projected lower boundary - buffer
→ SELL
```

This transformation is important because discretionary visual interpretation cannot be reproduced reliably by an automated backtest.

Every important trading decision should therefore be represented by an explicit rule in the EA.

## 8. Implementation

The strategy is implemented as a MetaTrader 5 Expert Advisor using MQL5.

The implementation should make important assumptions configurable through input parameters where appropriate.

Typical parameters include:

```text
Lot Size
Stop Loss
Take Profit
Maximum Spread
Maximum Positions
Signal Parameters
Breakout Parameters
Break Even
Trailing Stop
```

The exact parameters depend on the strategy.

The implementation should also account for relevant broker constraints such as:

```text
Minimum Volume
Maximum Volume
Volume Step
Stop Level
Freeze Level
Price Digits
Order Filling Mode
```

---

## 9. Compilation and Functional Verification

Before performance testing, the EA should first be checked for functional correctness.

At minimum:

```text
Source compiles successfully
EA initializes correctly
Signals can be generated
Orders can be opened
Orders can be closed
Stop Loss functions correctly
Take Profit functions correctly
Position management functions correctly
No obvious runtime failure prevents the strategy from operating
```

A successful compilation does **not** mean that the trading strategy passes.

It only means that the implementation is ready for empirical testing.

Where available, preserve:

```text

Trading distribution charts
MFE / MAE charts
Holding-time chart
```

For example:


The original report should be preserved rather than replaced by manually typed statistics.

## 12. Core Evaluation Metrics

The following metrics should be recorded when available.

### Net Profit

```text
Net Profit = Gross Profit + Gross Loss
```

Positive net profit is necessary for a profitable historical test but is not sufficient on its own to establish robustness.

### Profit Factor

```text
Profit Factor = Gross Profit / |Gross Loss|
```

Interpretation:

```text
PF > 1.0 → historical gross profit exceeds historical gross loss
PF = 1.0 → approximately break-even before considering other factors
PF < 1.0 → historical gross loss exceeds historical gross profit
```

### Expected Payoff

Expected Payoff measures average historical profit or loss per trade.

Negative expected payoff indicates negative historical expectancy for the tested sample.

### Drawdown

Both balance and equity drawdown should be recorded.

Important values include:

```text
Balance Drawdown
Equity Drawdown
Absolute Drawdown
Maximum Drawdown
Relative Drawdown
```

### Sharpe Ratio

When supplied by MT5, the Sharpe Ratio should be recorded as an additional risk-adjusted performance metric.

It should not be used as the sole PASS/FAIL criterion.

### Win Rate

```text
Win Rate =
Winning Trades / Total Trades
```

Win rate should always be interpreted together with average winning and losing trade sizes.

A high win rate does not automatically imply profitability.

### Average Winner / Loser

Compare:

```text
Average Profit Trade
Average Loss Trade
```

This helps determine how the realized payoff distribution interacts with the win rate.

### Consecutive Losses

Maximum consecutive losses are recorded to identify historical losing-streak behavior.

### Holding Time

Where available:

```text
Minimum Holding Time
Average Holding Time
Maximum Holding Time
```

This helps classify actual EA trading behavior.

## 13. PASS / FAIL Classification

Every tested EA should receive an explicit research status.

Possible statuses:

```text
PASS
FAIL
UNVERIFIED
```

### PASS

`PASS` means the tested configuration satisfies the repository's defined acceptance criteria and has supporting evidence.

A positive backtest alone should not automatically be interpreted as proof of a robust or production-ready trading system.

### FAIL

An EA is classified as `FAIL` when the tested configuration clearly fails the research objective.

Examples include:

```text
Negative Net Profit
Profit Factor < 1.0
Negative Expected Payoff
Unacceptable Drawdown
Execution failure
Insufficient implementation correctness
```

The exact reason should be recorded.

### UNVERIFIED

Use `UNVERIFIED` when evidence is insufficient to make a reliable PASS/FAIL decision.

Examples:

```text
Missing Strategy Tester report
Incomplete test
Unknown test settings
Insufficient evidence
Implementation not yet tested
```

---

## 14. Negative Results

Failed strategies are retained.

A failed EA is still useful research evidence.

Example:

```text
EA-058_Wedge_Break

Net Profit    = -$267.40
Profit Factor = 0.77
Equity DD     = 26.97%

Status = FAIL
```

Removing failed experiments would create survivorship bias in the repository.

The failed baseline also provides a reference against which later modifications can be measured.

---

## 15. Baseline Method

The first fully documented implementation and backtest can be retained as a baseline.

Future modifications should be compared against that baseline.

For example:

```text
EA-058_Wedge_Break
        │
        ├── Baseline implementation
        │
        ├── Baseline backtest
        │
        ↓
Future hypothesis
        │
        ├── Modify one research variable
        │
        ├── Backtest
        │
        └── Compare against baseline
```

The baseline should not be overwritten simply because a later version performs better.

---

## 16. Future Experiments

Future research should ideally modify a limited number of variables at a time.

Potential research dimensions include:

```text
Entry confirmation
Trend filters
Volatility filters
Trading sessions
Pattern thresholds
Stop Loss
Take Profit
Break Even
Trailing Stop
Timeframe
```

Changing many components simultaneously makes it difficult to determine which change caused the observed performance difference.

The preferred research loop is:

```text
Baseline
   ↓
Single hypothesis
   ↓
Controlled modification
   ↓
Backtest
   ↓
Compare
   ↓
Keep evidence
```

---

## 17. Optimization

Parameter optimization should be treated separately from initial hypothesis validation.

Recommended order:

```text
1. Implement baseline strategy
2. Run baseline test
3. Record baseline result
4. Identify a specific weakness or hypothesis
5. Modify or optimize
6. Run new test
7. Compare against baseline
```

Optimization should not erase the original baseline.

A highly optimized in-sample result should also not automatically be treated as evidence of future profitability.

---

## 18. Reproducibility

A research result should contain enough information for another researcher to understand what was tested.

At minimum, preserve:

```text
EA source code
EA identifier
Symbol
Timeframe
Test period
Important inputs
Initial deposit
Lot size
Leverage when relevant
Data quality
Original Strategy Tester evidence
Key performance metrics
Research status
```

If any important information is unknown, it should be marked as unknown rather than inferred.

---

## 19. Separation of Evidence and Interpretation

The repository distinguishes between:

```text
FACT
↓
Directly reported by source code or Strategy Tester evidence

OBSERVATION
↓
Description derived from those results

HYPOTHESIS
↓
Explanation that still requires testing
```

Example:

```text
FACT:
Profit Factor = 0.77

OBSERVATION:
Gross losses exceeded gross profits.

HYPOTHESIS:
False wedge breakouts may be contributing to the negative expectancy.
```

The hypothesis must not be presented as a proven cause until separately tested.

## 21. Research Integrity

The repository follows these rules:

```text
Do not fabricate results.

Do not report metrics without evidence.

Do not hide failed experiments.

Do not replace original evidence with improved numbers.

Do not describe an untested strategy as profitable.

Do not confuse successful compilation with successful strategy validation.

Do not infer missing test parameters.

Preserve original baseline evidence.

Separate facts from hypotheses.

Record negative results.
```

---

## 22. Disclaimer

All Expert Advisors, source code, research notes, and backtest results in this repository are provided for research and educational purposes.

Historical backtest performance does not guarantee future performance.

A Strategy Tester result demonstrates only how a specific implementation behaved under the recorded historical test conditions.

It does not establish that the strategy will produce the same result in live trading.
