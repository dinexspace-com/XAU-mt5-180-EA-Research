# Research & Backtesting Methodology

## 1. Purpose

This document defines the standard methodology used to research, implement, backtest, and evaluate Expert Advisors in this repository.

The objective is to maintain a research process that is:

- Reproducible
- Evidence-based
- Transparent
- Comparable across EA versions
- Resistant to overfitting

An EA is not considered successful simply because:

- the code compiles;
- a backtest completes;
- one parameter set is profitable;
- or one historical period produces positive results.

Every conclusion must be supported by documented test evidence.

---

## 2. Research Workflow

Each EA follows the same basic research process:

```text
Trading Idea
     ↓
Define Hypothesis
     ↓
Implement EA
     ↓
Compile & Technical Check
     ↓
Baseline Backtest
     ↓
Analyze Results
     ↓
PASS / FAIL
     ↓
Research Questions
     ↓
Controlled Experiments
     ↓
Robustness Validation
     ↓
Forward / Demo Testing
     ↓
Live Consideration
```

Each stage should produce evidence before moving to the next validation stage.

---

# 4. Stage 1 — Trading Idea

Every EA begins with a clearly defined trading idea.

Examples of possible concepts include:

```text
Trend continuation
Mean reversion
Breakout
Pullback
VWAP interaction
Volatility expansion
Session behavior
Momentum
```

The idea alone is not evidence of an edge.

It must be converted into a testable hypothesis.

---

# 5. Stage 2 — Define the Hypothesis

Before optimization, the strategy hypothesis should be stated explicitly.

Example structure:

```text
IF
market condition A occurs

AND
confirmation B occurs

THEN
condition C may have a higher probability of occurring
```

For example:

```text
Price approaches a reference level
        +
Directional confirmation occurs
        ↓
Continuation may follow
```

The hypothesis must be specific enough to implement and backtest.

---

# 6. Stage 3 — EA Implementation

The hypothesis is converted into an MQL5 Expert Advisor.

Each EA receives a unique identifier.

Example:

```text
EA-034_VWAP_Pullback
```

Recommended naming convention:

```text
EA-XXX_StrategyName
```

where:

```text
XXX = unique sequential EA number
```

The source should be stored under:

```text
EAs/
└── EA-XXX_StrategyName/
    ├── EA-XXX_StrategyName.mq5
    └── README.md
```

---

# 7. EA Documentation

Each EA README should document at minimum:

## Strategy

- Strategy concept
- Entry logic
- Exit logic
- Filters
- Position management

## Parameters

Examples:

```text
Lot Size
Stop Loss
Take Profit
Maximum Spread
Maximum Positions
Break Even
Trailing Stop
Magic Number
Strategy-specific filters
```

## Implementation Notes

Any behavior that may affect research results should be documented.

Examples:

- new-bar execution;
- tick execution;
- server-time dependency;
- indicator reset behavior;
- broker volume dependency;
- hard-coded thresholds;
- fixed lot sizing.

The documentation should describe what the EA actually does rather than what the strategy was intended to do.

---

# 8. Stage 4 — Technical Validation

Before evaluating profitability, the EA must first pass basic technical checks.

Minimum technical requirements:

```text
Code compiles
        ↓
EA loads correctly
        ↓
Strategy Tester runs
        ↓
Orders can be generated
        ↓
SL / TP function correctly
        ↓
Position management executes
        ↓
Backtest completes
```

A technical PASS does not mean the strategy is profitable.

It only means the implementation can proceed to strategy testing.

---

# 9. Stage 5 — Baseline Backtest

The first meaningful test should establish a baseline.

The baseline should be preserved unchanged.

Its purpose is to answer:

> Does the initial implementation show evidence of a trading edge under the documented test conditions?

The baseline should not be silently replaced after optimization.

Both successful and failed baseline tests are research evidence.

---

# 10. Backtest Environment

Each backtest should record enough information to reproduce the test.

At minimum:

| Field | Required |
|---|---|
| EA Name | Yes |
| EA Version | Recommended |
| Symbol | Yes |
| Timeframe | Yes |
| Test Period | Yes |
| Initial Deposit | Yes |
| Currency | Yes |
| Leverage | Yes |
| Broker / Data Source | Yes |
| History Quality | Yes |
| EA Inputs | Yes |

Where available, also retain:

```text
MT5 build
Number of bars
Number of ticks
Spread assumptions
Execution assumptions
```

---

# 11. Historical Data Quality

Backtest conclusions depend on the quality of the underlying market data.

When available, testing should use:

```text
Every tick based on real ticks
```

The reported history quality must be preserved in the evidence.

For example, the EA-034 baseline used:

```text
History Quality = 100% real ticks
```

A high-quality tick model improves test fidelity but does not guarantee that a strategy will perform similarly in live trading.

---

# 12. Baseline Parameters

All parameters used in a baseline test must be recorded.

Examples:

```text
Lot Size
Stop Loss
Take Profit
Break Even
Trailing Stop
Maximum Spread
Maximum Positions
Magic Number
Strategy-specific filters
```

Without the exact parameters, the test cannot be reliably reproduced.

---

# 13. Backtest Evidence

The original Strategy Tester output should be retained whenever possible.

Recommended structure:

```text
Backtest/
└── EA-XXX_StrategyName/
    ├── README.md
    ├── StrategyTesterReport.html
    ├── balance.png
    ├── distribution.png
    ├── mfemae.png
    └── holding.png
```

The original MT5 report should be treated as the primary evidence source for the test.

Summary README files should not replace the original report.

---

# 14. Core Performance Metrics

Backtest evaluation should consider multiple metrics rather than net profit alone.

Minimum metrics include:

| Metric | Purpose |
|---|---|
| Total Net Profit | Overall financial result |
| Profit Factor | Gross profit relative to gross loss |
| Expected Payoff | Average expectancy per trade |
| Maximum Drawdown | Capital risk |
| Total Trades | Sample size |
| Win Rate | Distribution of winning trades |
| Average Win | Typical winning outcome |
| Average Loss | Typical losing outcome |
| Sharpe Ratio | Risk-adjusted performance indicator |
| Recovery Factor | Profit relative to drawdown |

No single metric should determine strategy quality by itself.

---

# 15. Profit Factor

Profit Factor is:

```text
Profit Factor = Gross Profit / |Gross Loss|
```

Interpretation:

```text
PF > 1
Gross profits exceed gross losses

PF = 1
Approximate break-even before considering additional real-world effects

PF < 1
Gross losses exceed gross profits
```

A Profit Factor above 1 is necessary for a profitable historical result but is not sufficient evidence of robustness.

---

# 16. Expected Payoff

Expected Payoff represents average historical profit or loss per trade.

Conceptually:

```text
Expected Payoff
=
Total Net Profit / Total Trades
```

A negative Expected Payoff indicates negative historical expectancy under the tested configuration.

---

# 17. Drawdown

Drawdown must be evaluated alongside profitability.

Important metrics include:

```text
Balance Drawdown
Equity Drawdown
Absolute Drawdown
Maximum Drawdown
Relative Drawdown
```

A strategy producing profit with excessive drawdown may still be unsuitable.

Therefore:

```text
Profitability
+
Drawdown
+
Stability
```

must be evaluated together.

---

# 18. Sample Size

A small number of trades can produce misleading results.

The number of trades must therefore always be documented.

For example:

```text
10 trades
```

provides much weaker evidence than:

```text
1,000 trades
```

However, a large sample does not automatically validate a strategy.

If the underlying edge is negative, a larger sample may simply provide stronger evidence of that failure.

---

# 19. Win Rate and Payoff

Win rate must not be interpreted alone.

A strategy may have:

```text
Low Win Rate
+
Large Average Winner
+
Small Average Loser
```

and still be profitable.

Likewise:

```text
High Win Rate
+
Small Winners
+
Large Losses
```

can still produce negative expectancy.

Therefore evaluate:

```text
Win Rate
+
Average Win
+
Average Loss
+
Profit Factor
+
Expected Payoff
```

together.

---

# 20. Balance / Equity Curve

The balance and equity curves should be visually inspected.

Research should look for:

- persistent upward progression;
- persistent decline;
- prolonged stagnation;
- sudden dependence on a small number of trades;
- large drawdown clusters;
- unstable performance periods.

A smooth historical curve is not proof of future profitability.

However, a persistent downward curve is strong evidence that the tested configuration requires further research.

---

# 21. Long vs Short Analysis

BUY and SELL performance should be inspected separately when the Strategy Tester provides sufficient evidence.

Possible questions:

```text
Do BUY and SELL have similar expectancy?

Is one direction responsible for most losses?

Does the strategy behave differently in bullish and bearish regimes?
```

A directional filter should not be introduced merely because one side performed better in a single historical test.

It should become a new hypothesis and be independently tested.

---

# 22. Time Distribution Analysis

Where available, analyze performance by:

```text
Hour
Trading session
Weekday
Month
```

The objective is to understand strategy behavior.

It is not automatically an instruction to remove historically weak periods.

For example:

```text
Baseline shows losses around hour X
```

does not automatically justify:

```text
Disable trading at hour X
```

Doing so after inspecting the same dataset can introduce overfitting.

Instead:

```text
Observation
    ↓
New hypothesis
    ↓
Independent test
```

---

# 23. MFE / MAE Analysis

Where available, use:

```text
MFE = Maximum Favorable Excursion
MAE = Maximum Adverse Excursion
```

These measurements help investigate what happens to trades after entry.

Possible research questions include:

```text
Do winners typically move strongly in favor before exit?

How far do winning trades move against the entry first?

Are Stop Loss distances unnecessarily large?

Are profitable excursions being lost before exit?

Does the Take Profit capture typical favorable movement?
```

MFE/MAE observations should generate hypotheses.

They should not automatically generate optimized parameters.

---

# 24. Holding-Time Analysis

Trade holding time can reveal whether the implementation behaves as expected.

Record where available:

```text
Minimum holding time
Average holding time
Maximum holding time
```

Possible research questions:

```text
Are most winners short-lived?

Do losing trades remain open longer?

Does performance deteriorate after a certain duration?
```

Any resulting time-based exit must be tested independently.

---

# 25. Stage 6 — PASS / FAIL

Each baseline test should receive an explicit research status.

Possible statuses:

```text
PASS
FAIL
INCONCLUSIVE
```

### FAIL

Use when the evidence clearly shows the tested configuration does not meet the research objective.

Examples:

```text
Negative net profit
Negative expectancy
Profit Factor below 1
Unacceptable drawdown
```

### INCONCLUSIVE

Use when the evidence is insufficient to make a reliable decision.

Examples:

```text
Too few trades
Insufficient historical period
Incomplete data
Technical anomaly
```

### PASS

PASS should mean:

> The strategy has passed the requirements defined for the current research stage.

It does **not** automatically mean:

```text
Ready for live trading
```

---

# 26. Failed Strategies Must Be Preserved

Failed experiments are part of the research record.

Do not delete an EA simply because:

```text
Net Profit < 0
```

Instead preserve:

```text
Hypothesis
Implementation
Parameters
Backtest
Evidence
Conclusion
```

A failed experiment helps prevent repeating the same test and provides a baseline for future improvements.

---

# 27. Stage 7 — Research Questions

After a baseline test, observations should be converted into explicit research questions.

Recommended format:

```text
RQ-01 — Entry Logic
RQ-02 — Exit Logic
RQ-03 — Trading Session
RQ-04 — Long vs Short
RQ-05 — Stop Loss
RQ-06 — Take Profit
RQ-07 — Trade Management
RQ-08 — Market Regime
```

Each research question should isolate one meaningful strategy component where possible.

---

# 28. Controlled Experiments

The preferred research process is:

```text
Baseline
   ↓
Change ONE meaningful component
   ↓
Backtest
   ↓
Compare
```

Avoid:

```text
Change entry
+
Change SL
+
Change TP
+
Change session
+
Change trailing
+
Change indicator
        ↓
Backtest
```

If many components change simultaneously, it becomes difficult to determine why performance changed.

---

# 29. Experiment Naming

Future experiments should be identifiable.

Example:

```text
EA-034 Baseline

EXP-034-01_NoTrailing
EXP-034-02_VWAPDistance
EXP-034-03_SessionFilter
EXP-034-04_LongOnly
EXP-034-05_ShortOnly
```

Each experiment should document:

```text
Hypothesis
Change from baseline
Parameters
Test environment
Result
Evidence
PASS / FAIL
Conclusion
```

---

# 30. Baseline Comparison

Every experiment should be compared against the original baseline.

Example:

| Metric | Baseline | Experiment |
|---|---:|---:|
| Net Profit | — | — |
| Profit Factor | — | — |
| Expected Payoff | — | — |
| Max Drawdown | — | — |
| Total Trades | — | — |
| Win Rate | — | — |

The objective is not merely to determine whether the experiment made more money.

It is to determine whether the proposed hypothesis improved the strategy in a meaningful and reproducible way.

---

# 31. Avoiding Overfitting

Optimization creates a major research risk:

```text
Historical data
      ↓
Search many parameter combinations
      ↓
Select best historical result
      ↓
Apparently excellent EA
```

This may simply produce a strategy fitted to historical noise.

Warning signs include:

- excessive parameter optimization;
- very narrow parameter ranges;
- many filters added after inspecting losses;
- removing individual losing periods;
- selecting only the best historical timeframe;
- selecting only the best symbol configuration;
- repeated optimization against the same dataset.

Optimization results should therefore be treated as hypotheses requiring further validation.

---

# 32. In-Sample vs Out-of-Sample

When a strategy begins showing promise, historical data should be separated where practical.

Conceptually:

```text
Historical Data
│
├── In-Sample
│     Research / development
│
└── Out-of-Sample
      Independent validation
```

The strategy is developed using the in-sample period.

The out-of-sample period should then test whether the observed edge persists on data not used to select the strategy configuration.

---

# 33. Robustness Testing

A promising EA should undergo additional robustness testing before forward testing.

Possible tests include:

```text
Different historical periods
Different market regimes
Parameter sensitivity
Spread sensitivity
Execution-cost sensitivity
Long / short decomposition
Session decomposition
Out-of-sample testing
```

The objective is not to prove that the EA works everywhere.

The objective is to determine whether the observed performance depends on fragile assumptions.

---

# 34. Parameter Sensitivity

A robust strategy should not depend entirely on one exact parameter combination.

Example:

```text
SL = 299 → bad
SL = 300 → excellent
SL = 301 → bad
```

would be suspicious.

More stable behavior across neighboring parameter values provides stronger evidence than a single isolated optimum.

---

# 35. Transaction Costs

Backtests should consider realistic trading conditions.

Relevant factors may include:

```text
Spread
Commission
Slippage
Execution latency
Swap
Broker conditions
```

A strategy with a small theoretical edge may fail when realistic costs are introduced.

---

# 36. Broker Dependency

XAUUSD specifications can vary between brokers.

Possible differences include:

```text
Symbol name
Digits
Point size
Spread
Contract size
Trading sessions
Server timezone
Volume data
Execution conditions
```

Therefore, a result on:

```text
XAUUSD.PRO
```

should not automatically be assumed to reproduce identically on another broker's XAUUSD symbol.

---

# 37. Forward Testing

Historical backtesting is not the final validation stage.

A promising strategy should eventually move to:

```text
Backtest
    ↓
Robustness Test
    ↓
Out-of-Sample
    ↓
Demo / Forward Test
```

Forward testing helps evaluate behavior under live market conditions not known when the strategy was developed.

---

# 38. Live Trading

An EA should not be described as live-ready merely because it passes a historical backtest.

Live consideration requires separate review.

Potential areas include:

```text
Strategy robustness
Execution behavior
Broker compatibility
Risk management
Operational stability
Forward-test evidence
Capital allocation
```

Approval for live deployment is outside the scope of a baseline backtest.

---

# 39. Evidence Principle

Every important research conclusion should have evidence.

Preferred structure:

```text
Claim
  ↓
Metric / Observation
  ↓
Original Artifact
  ↓
Conclusion
```

For example:

```text
Claim:
Baseline has negative expectancy

Evidence:
Expected Payoff = -0.36

Source:
Original MT5 Strategy Tester report

Conclusion:
Baseline FAIL
```

Avoid unsupported conclusions such as:

```text
"This strategy works."
```

without documented evidence.

---

# 40. Reproducibility Principle

Another researcher should ideally be able to determine:

```text
What was tested?
Which EA version?
Which parameters?
Which symbol?
Which timeframe?
Which period?
Which data?
What happened?
Where is the evidence?
What conclusion was made?
```

If these questions cannot be answered, the research record is incomplete.

---

# 41. Source of Truth

The original artifacts are the primary evidence.

Priority:

```text
1. EA source code
2. Original MT5 Strategy Tester report
3. Original Strategy Tester charts
4. Backtest README
5. Research notes
```

README files summarize evidence.

They do not replace the original source code or Strategy Tester report.

# 42. Current Reference Example — EA-034

The first documented application of this methodology is:

```text
EA-034_VWAP_Pullback
```

Baseline:

```text
Symbol          = XAUUSD.PRO
Timeframe       = M1
Period          = 2026.01.02 – 2026.04.01
Initial Deposit = $1,000
History Quality = 100% real ticks
Total Trades    = 939
```

Result:

```text
Net Profit       = -$335.57
Profit Factor    = 0.84
Expected Payoff  = -$0.36
Sharpe Ratio     = -5.00
Win Rate         = 29.82%
Max Equity DD    = 36.07%
```

Status:

```text
BASELINE = FAIL
```

This failed result remains valuable because it establishes a reproducible baseline for future EA-034 experiments.

# 43. Research Standard

The repository follows this principle:

> A backtest is evidence, not proof.

And:

> A failed experiment is a research result, not something to hide.

The intended progression is:

```text
Idea
 ↓
Hypothesis
 ↓
Implementation
 ↓
Baseline
 ↓
Evidence
 ↓
Controlled Research
 ↓
Robustness
 ↓
Forward Validation
 ↓
Live Consideration
```

The objective is not to find the best-looking historical equity curve.

The objective is to determine whether a trading hypothesis can demonstrate a sufficiently reproducible and robust edge under controlled testing.
