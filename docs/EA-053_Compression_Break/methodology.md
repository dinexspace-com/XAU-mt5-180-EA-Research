# EA Research & Backtesting Methodology

## Purpose

This document defines the research, implementation, backtesting, and validation methodology used in the XAUUSD MT5 EA research repository.

The purpose of the methodology is to ensure that every Expert Advisor is evaluated through a consistent and reproducible process.

A strategy is not considered successful simply because it can be coded, generates trades, or produces one profitable backtest.

Research evidence must be preserved so that the development history of each EA can be reviewed and reproduced.

---

## Research Workflow

The standard workflow is:

Research Idea → Trading Hypothesis → Explicit Rules → MQL5 Implementation → Baseline Backtest → Analysis → Controlled Modification → Retest → Validation

Each stage has a different purpose.

Research establishes the hypothesis.

Implementation converts the hypothesis into deterministic rules.

Baseline testing determines how the original implementation behaves.

Further experiments investigate weaknesses or possible improvements.

Validation determines whether an observed improvement remains present outside the data used to develop it.

---

## 1. Research Hypothesis

Every EA begins with a trading hypothesis.

The hypothesis must describe a market behavior that can eventually be converted into explicit rules.

For example, EA-053 investigates the hypothesis:

**A sequence of progressively contracting candle ranges followed by a confirmed breakout may contain useful directional information.**

At this stage, profitability must not be assumed.

The hypothesis is simply something that can be tested.

---

## 2. Rule Definition

Before evaluating performance, the strategy must be converted into deterministic rules.

The rules should define, where applicable:

- Market and symbol
- Timeframe
- Signal structure
- Entry conditions
- BUY conditions
- SELL conditions
- Stop Loss
- Take Profit
- Position sizing
- Spread restrictions
- Position limits
- Break Even behavior
- Trailing Stop behavior
- Exit conditions

A rule should be sufficiently explicit that the same market data produces the same intended decision when the same EA version and configuration are used.

Ambiguous discretionary interpretation should not be introduced into a mechanical EA after testing has started.

---

## 3. Implementation

The research rules are implemented as a MetaTrader 5 Expert Advisor using MQL5.

Each EA has its own directory:

EAs/EA-XXX_Strategy_Name/

The directory contains at minimum:

EA-XXX_Strategy_Name.mq5  
README.md

The `.mq5` file contains the executable strategy logic.

The EA README documents what the implementation actually does.

Documentation should describe the code being tested rather than an intended strategy that has not yet been implemented.

---

## 4. Baseline Version

The first complete implementation becomes the baseline.

The purpose of the baseline is not to produce an attractive result.

Its purpose is to establish the initial measurable behavior of the hypothesis.

Once tested, baseline evidence should be preserved.

A failed baseline remains useful research evidence.

It must not be deleted simply because later versions perform better.

---

## 5. Backtest Environment

Backtests are performed using MetaTrader 5 Strategy Tester.

The test record should preserve enough information to identify the environment used for the experiment.

Important fields include:

- EA name/version
- Symbol
- Timeframe
- Test period
- Historical data quality
- Initial deposit
- Currency
- Leverage
- Lot size
- EA input parameters
- Number of bars
- Number of ticks
- Number of trades

Where available, 100% real-tick history is preferred for the primary research evidence.

The exact broker symbol and trading environment must be recorded because XAUUSD specifications can differ between brokers.

---

## 6. Backtest Evidence

Backtest evidence is stored separately from EA source code.

Directory convention:

Backtest/EA-XXX_Strategy_Name/

The original MT5 Strategy Tester report should be retained.

Associated charts generated by the report should also be retained where applicable.

The HTML Strategy Tester report is treated as the primary numerical evidence.

The README inside the backtest directory summarizes the experiment and its result.

Original evidence should not be manually altered to make a result appear better.

---

## 7. Core Performance Metrics

At minimum, the following metrics should be reviewed:

### Total Net Profit

Measures the final trading profit or loss generated during the test.

Positive Net Profit alone is not sufficient to validate an EA.

### Profit Factor

Profit Factor is calculated conceptually as:

Profit Factor = Gross Profit / Gross Loss

A value below 1 indicates that losses exceeded profits during the tested sample.

A value above 1 indicates positive gross expectancy during that sample, but does not by itself prove robustness.

### Expected Payoff

Expected Payoff measures the average result per trade.

Negative Expected Payoff indicates negative average expectancy in the tested sample.

### Drawdown

Both balance and equity drawdown should be reviewed.

Important values include:

Balance Drawdown Absolute  
Balance Drawdown Maximal  
Balance Drawdown Relative  
Equity Drawdown Absolute  
Equity Drawdown Maximal  
Equity Drawdown Relative

Drawdown must be evaluated together with return.

A profitable EA with excessive drawdown should not automatically be accepted.

### Sharpe Ratio

Sharpe Ratio is used as one measure of risk-adjusted performance.

It should not be interpreted independently from Net Profit, drawdown, trade count, and equity behavior.

### Recovery Factor

Recovery Factor provides information about performance relative to drawdown.

Negative recovery is a clear warning sign in a losing baseline.

### Trade Count

Trade count is important for determining how much evidence exists.

A very small number of trades can produce misleading performance statistics.

A large sample is useful, but large sample size does not rescue a strategy with negative expectancy.

### Win Rate

Win rate is reviewed separately for:

Overall trades  
BUY trades  
SELL trades

Win rate alone is not a profitability metric.

It must be evaluated together with average winning trade and average losing trade.

---

## 8. Equity Curve Review

Numerical metrics are not reviewed in isolation.

The balance and equity curves should also be inspected.

Important characteristics include:

- Overall direction
- Stability
- Long periods of stagnation
- Sudden large losses
- Dependence on a small number of trades
- Persistent deterioration
- Abnormal changes in behavior

A steadily deteriorating curve is evidence against the tested configuration even if isolated periods are profitable.

---

## 9. Trade Distribution Review

Trade-level statistics should be examined when available.

Relevant measurements include:

- Winning trades
- Losing trades
- Average winning trade
- Average losing trade
- Largest winning trade
- Largest losing trade
- Consecutive wins
- Consecutive losses
- BUY performance
- SELL performance
- Holding time
- MFE
- MAE

The purpose is to identify where strategy performance originates.

Observations discovered during this analysis are research hypotheses until they are independently tested.

---

## 10. Baseline PASS / FAIL

The baseline test answers a simple question:

**Does the original implemented configuration demonstrate a usable positive edge in the tested sample?**

The exact decision should consider multiple metrics rather than a single number.

A configuration should normally be considered FAIL when evidence includes conditions such as:

- Negative Total Net Profit
- Profit Factor below 1
- Negative Expected Payoff
- Unacceptable drawdown
- Strongly deteriorating equity curve
- Clearly unfavorable risk-adjusted performance

A failed baseline does not mean the research project failed.

It means the tested configuration failed.

This distinction is important.

## 12. Failed Baselines

Failed strategies must not be hidden from the repository.

Negative results provide useful information.

They show:

- Which hypothesis was tested
- How it was implemented
- Which parameters were used
- Which market period was tested
- How many trades occurred
- Which weaknesses appeared

Preserving failed experiments also reduces the risk of unknowingly repeating the same unsuccessful configuration later.

---

## 13. Modification After Baseline

After baseline analysis, modifications may be investigated.

Potential research variables can include:

- Signal quality
- Market regime
- Trend filters
- Volatility filters
- Trading sessions
- Breakout confirmation
- Stop Loss behavior
- Take Profit behavior
- Break Even behavior
- Trailing Stop behavior
- Spread conditions
- BUY/SELL asymmetry

A potential improvement is not automatically accepted merely because it appears reasonable.

It must be tested.

---

## 14. Controlled Experiments

Whenever practical, modifications should be introduced in a controlled manner.

The preferred principle is:

**Change → Test → Compare**

rather than:

**Change many things → Optimize everything → Keep the best result**

The first approach makes it easier to understand why performance changed.

If multiple parameters are optimized simultaneously, the resulting configuration should be treated as a candidate requiring further validation rather than proof of a robust strategy.

---

## 15. Optimization

Optimization is a research tool.

It is not validation.

Optimization can identify parameter combinations that performed well on historical data.

However, selecting the best historical combination creates a risk of overfitting.

Therefore:

Optimized result ≠ Validated result

A strong optimization result should progress to additional testing.

The original baseline should remain available for comparison.

---

## 16. Overfitting Control

A strategy may appear highly profitable because its rules or parameters have adapted too closely to the historical period used during development.

Warning signs include:

- Extremely narrow profitable parameter ranges
- Large performance changes from small parameter changes
- Excellent optimization results but weak performance on new periods
- Profit concentrated in a small number of trades
- Performance dependent on one short market regime
- Repeated optimization against the same historical sample

The objective is not to find the historically perfect parameter set.

The objective is to determine whether a trading concept exhibits behavior that remains useful under different conditions.

---

## 17. Out-of-Sample Testing

Promising configurations should be tested on historical data that was not used to select their parameters.

Conceptually:

Development Data → Build / Optimize

Separate Data → Out-of-Sample Test

The out-of-sample result should not be used repeatedly for optimization, otherwise it gradually becomes part of the development data.

A configuration that performs well only on its optimization period should not be considered validated.

---

## 18. Forward Testing

After historical validation, a promising EA can progress to forward testing.

Forward testing evaluates behavior on market data arriving after the strategy configuration has been selected.

This stage helps identify issues that historical backtests may not fully represent.

Examples include:

- Spread behavior
- Slippage
- Broker execution
- Symbol specification
- Trading-session behavior
- Order rejection
- Stop-distance restrictions
- Live tick behavior

Forward testing should occur before considering live production use.

---

## 19. Production Readiness

An EA is not production-ready simply because the source code compiles or one backtest is profitable.

The research progression is:

Research Hypothesis  
→ Implementation  
→ Baseline  
→ Analysis  
→ Controlled Experiments  
→ Candidate Configuration  
→ Out-of-Sample Validation  
→ Forward Test  
→ Production Review

Each stage should preserve its evidence.

Live deployment requires a separate decision after validation.

---

## 20. Reproducibility

Every important experiment should be reproducible.

A reviewer should be able to determine:

What EA was tested?  
What code version was used?  
What symbol was used?  
What timeframe was used?  
What historical period was used?  
What parameters were used?  
What deposit and leverage were used?  
What historical data quality was available?  
What result was produced?

If these questions cannot be answered from repository evidence, the experiment should not be treated as fully documented.

## 22. Evidence Hierarchy

When evaluating an EA, evidence should be considered in the following order:

Source Code  
→ Exact Test Configuration  
→ Original MT5 Report  
→ Supporting Charts  
→ Backtest README  
→ Research Interpretation

Interpretation must not contradict the original test evidence.

If documentation and the original MT5 report disagree, the original report and source implementation should be investigated before drawing conclusions.

---

## 23. Documentation Principle

The repository distinguishes between:

**Fact** — directly supported by code or test evidence.

**Observation** — behavior visible in the available experiment.

**Hypothesis** — a possible explanation that requires testing.

**Validated Result** — a conclusion that has survived the required validation process.

These categories should not be mixed.

For example:

“BUY win rate was 50.80% in the EA-053 baseline” is an observation.

“BUY signals are inherently better than SELL signals” is a hypothesis and cannot be concluded from that observation alone.

---

## 24. Research Integrity

The repository is intended to preserve the complete research process rather than only successful results.

Therefore:

Do not delete failed baselines.

Do not overwrite original MT5 evidence.

Do not present optimization as validation.

Do not infer live profitability from historical backtests.

Do not change historical documentation to match later versions.

Do not label an EA production-ready without appropriate validation.

Positive and negative results are both part of the research record.
